基于图的增量 wiki

用图算法提供概念依据，用增量引擎保证更新又快又准

graphify · neug · wiki

01 / 背景

LLM-wiki pattern

Andrej Karpathy 提出的一种用 LLM 持续维护知识库的模式

  • 不只是提问时检索（RAG），而是持续维护一个结构化 wiki
  • 首次构建需要 LLM 全量读取原始内容，消耗大量 tokens
  • 之后每次加入新内容，增量更新受影响的页面
  • 维护交叉引用、更新摘要、标注矛盾——bookkeeping 由 LLM 完成

知识是"编译一次、持续更新"的。在个人知识库场景下，规模小，这套流程够用。

02 / 问题

规模变大后，结构性问题浮现

当内容源变大、变复杂——代码仓库几百个文件，企业知识库上千篇文档——

核心问题是：谁来决定"概念边界"？

LLM 读了内容，自己决定怎么组织页面。这个判断完全依赖 LLM 的主观理解。

02 / 问题

问题一：概念归属不稳定

  • 同一组内容，LLM 这次分成三篇，下次合成一篇
  • 不是 LLM 能力不行，而是没有结构依据——在读文本，不在读"关系"
  • 概念边界在每次 ingest 时都可能漂移
02 / 问题

问题二：变更影响范围不一定准确

  • 加了一个新源，LLM 需要判断"这会影响哪些已有 wiki 页面"
  • 读了新源，再扫已有页面看哪些相关
  • 这个"猜"的过程本身消耗 tokens，而且可能不准确
02 / 问题

问题三：没有质量指标

  • 一个概念的内聚度够不够？
  • 两个概念之间有没有意想不到的关联？
  • 当前概念里，最相关的文件是哪些？

这些在文本层面看不出来，需要图结构才能算。

02 / 示例

示例：LLM 直接处理 neug repo

项目规模1,642 个源文件
增量变更47 文件改动，+14,243 行（新增 pattern matching 模块）
全量构建读 1,642 个文件 → 百万级 tokens
增量更新读 47 个变更文件 → tokens 少了

但：哪些 wiki 页面受影响？靠 LLM 猜

  • LLM 只读 47 个变更文件，不知道引用关系会影响哪些已有 wiki 页面
  • 已有模块的 wiki 没更新，说的还是旧信息 → 知识腐化
03 / 解法

用图提供结构依据

在 LLM 和原始内容之间加一层图

原始内容 → 图数据库 → 概念组（图算法确定） → LLM 命名 + 写 wiki

概念边界由算法确定，不依赖 LLM 主观判断——确定性、可复现、不漂移

03 / 解法

解法：Graphify

  • 概念归并用 Leiden/Louvain 聚类算法：根据节点间实际关系计算，不是 LLM 猜的
  • wiki 有质量指标：内聚度、跨概念连接、枢纽节点——图结构天然给出
  • LLM 只做理解和表达：给它一个已确定的概念组，让它命名、写文章，而不是同时决定"怎么分"和"写什么"
04 / 示例

示例：Graphify 全量聚类 — 优势

图规模28,928 节点 · 52,501 边 · 1,642 源文件
全量聚类结果2,553 个概念组

LLM 只需理解 2,553 个概念组

不用读 1,642 个源文件

tokens 从 O(N) 降到 O(K)

04 / 新问题

但图也要更新

内容变了，图要跟着变，概念归组也可能变化。

如果全量重建图 + 全量重新归组：

  • 重建成本吃掉了结构优势
  • 重新归组的结果不稳定，概念编号会漂移
  • 和 LLM-wiki 里 LLM 判断漂移是同一个问题，只是换了一层
04 / 示例

示例：Graphify 全量聚类 — 增量不足

增量变更47 文件改动，+14,243 行
  • 全量重新跑 Leiden → 旧 2,438 vs 新 2,553
  • community ID 会漂移，无法直观 diff 两个 3K 行 JSON
  • 只能全量重新 LLM labeling → 所有概念组重新命名

有图算法确定概念边界，但缺少增量能力，更新成本仍是 O(K) 全量。

05 / 解法

neug 提供三层增量能力

freeze-assign Leiden Cypher 变更检测 COPY TEMP 临时图
  • 增量归组：已有概念组冻结，只分配新内容
  • 变更检测：Cypher group by 精确计算社区级变化
  • 临时图计算：增量分析不污染原图
05 / 解法

1. 增量归组（freeze-assign Leiden）

  • 已有概念组保持不变，只对新增内容分配概念组
  • 不只是快——更重要的是概念稳定性
  • 原来叫"compiler"的概念，增量后还是"compiler"。不漂移，可 diff

对比 LLM：每次 ingest 都可能重新理解组织结构。freeze-assign 给了结构层面的稳定性保证。

-- freeze-assign Leiden
CALL leiden('g', {freeze_assign: true})
YIELD node, community,
     previous_community
RETURN node.id,
       community,
       previous_community
ORDER BY node.id;

旧节点: previous_community 有值（冻结）
新节点: previous_community = NULL

05 / 解法

2. Cypher 驱动的变更检测

  • 增量归组后，用 Cypher 查询语言对图做分析
  • 写 group by 语句，按社区聚合计算变更统计
  • 统计每个概念组的新增成员数、旧成员存活数
  • 据此判定：stable changed new dissolved
-- group by 社区，计算变更统计
WITH community, count(*) AS total,
     count(previous_community)
       AS old_members
WITH community, total, old_members,
     total - old_members AS new_members
RETURN community, total,
       old_members, new_members,
  CASE
    WHEN old_members = 0 THEN 'new'
    WHEN new_members = 0 THEN 'stable'
    ELSE 'growth'
  END AS change_type
ORDER BY change_type, community;
05 / 解法

3. 临时图计算（COPY TEMP）

  • COPY TEMP FROM 导入临时边，不修改持久图数据
  • 增量归组时构建临时聚合视图（如符号级→文件级）
  • 用完即弃，原图保持不变

增量计算不会对已有图产生副作用——每次分析都在隔离的临时结构上完成。

-- 导入临时边，不修改持久图
COPY TEMP file_edges
  FROM 'edges.csv' (DELIM=',');

-- 在临时图上跑聚类
CALL project_graph('g2',
  ['file_node'],
  {'[file_node, file_edges,
    file_node]': ''});
CALL leiden('g2',
  {concurrency: 4});

-- 用完即弃，原图不变
CALL drop_projected_graph('g2');

05 / 示例

端到端流程


test1 (基线) → 全量构建图 + Leiden + 生成 wiki
      ↓
test2 (增量) → 只提取 47 个变更文件
      ↓
freeze-assign Leiden → 旧节点冻结，只分配新节点
      ↓
Cypher group by → 2,413 stable / 21 changed / 119 new / 4 dissolved
      ↓
增量 wiki → 只有 144 个概念组需要 LLM 更新

代码 repo 是 POC 的第一个场景，但不是唯一场景。
任何"有结构、会变化的内容源"都适用。

06 / 总结

定位总结

LLM-wiki+ 图+ neug 增量
概念边界LLM 判断图算法确定算法 + 增量稳定
变更检测LLM 读文本猜全量重建Cypher 精确计算
更新成本每次 ingest 扫描O(K) 全量O(ΔK) 只处理变化
概念稳定性可能漂移编号变freeze-assign 不变
计算安全性——临时图隔离

不是替代，而是各司其职

图：结构化部分

  • 图算法确定概念边界
  • Cypher 查询精确计算变更
  • 增量算法保证更新又快又稳

大模型：语义部分

  • 理解概念组，生成 wiki 文章
  • 给概念组命名、归纳
  • 负责表达，不负责决定结构
